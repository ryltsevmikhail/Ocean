- Options: optional `protocol: 'legacy' | '2026-07-28'` (legacy default; explicit pin on modern), `resolveCredential(reference, frozenConnection): string | null`, `githubIssueReadOnly?: boolean`, `stdio?: { profileRoot: string; workspaces: Readonly<Record<string,string>> }`, `prepareDispatch?(invocationId): void | Promise<void>`, `refreshNeeded?(connectionId): void`. A host enrolls a dedicated isolated workspace per connection; any change to that mapping/profile must invalidate the old authority tuple before discovery. The GitHub option is restricted to the exact qualified HTTPS endpoint and adds only the fixed read-only/issue_read headers. This is not an arbitrary header channel.
- `discover(connection, {signal, deadlineMs, authorizeMetadata(): boolean})` returns a frozen candidate `Omit<ServiceCatalogSnapshot,'id'>`: connection ID, config/trust/credential revisions, complete, observedAt, tools and plain protocol/client provenance. No SDK state crosses the boundary. The instance retains the full tool, including SDK-specific metadata, with a SHA-256 digest of canonical JSON over the **entire** definition. Malformed, duplicate, incomplete, unsupported tools capability or oversized catalogs cannot publish. Credentials resolve only via the connection's explicit reference, once at discovery. Missing credentials fail closed. No environment/account search or identity upgrade.
- Begin refresh/durably publish through the accepted owner service. `activate(candidate,snapshot,confirmPublished): boolean` requires original object identity, an unspent usable candidate, exact snapshot content apart from the new ID, and synchronous proof of **current durable publication**. A serialized/cloned candidate is inert. The callback must check the current tuple/ID and persisted snapshot in the owner's store, not merely remember a prior insert. Rejected/unpublished candidates must be disposed by their owner. `disposeCandidate(candidate)` and `close()` resolve to `{status:'confirmed'|'never_started'|'unknown'}`; unknown latches execution/discovery off. Evidence concerns local retirement, not vendor effects.
- `invoke(ServiceCallInvocation)` implements the existing C3 port; no DB, grant creation or owner broker in the adapter. It selects the active session for the exact catalog/config/trust/credential tuple and admitted definition. Its immutable credential and original full SDK tool are pinned through async preparation. Previously admitted calls keep their own session until they finish; C3's synchronous final SQLite guard decides whether authority still holds. Calls never list, initialize, negotiate a fallback, reconnect or change account. If a session disappears execution is unavailable; durable grants are untouched. TTL/list-change only deliver a single hint per active generation. The owner must authorize/deduplicate any actual refresh separately.

The shared client profile uses the public SDK root and stdio entries, explicit version mode, no input auto-fulfillment, zero default cache TTL, zero reconnection retries, insufficient-scope throw, redirect error. Explicit list uses refresh and an explicitly supplied toolDefinition bypasses implicit business lookup/refetch. `InvocationSend` closes on completion/error, checks a monotonic deadline, caller signal and one-shot owner guard at the final fetch or public stdio send, **after** asynchronous preparation. A server answer (including vendor error) is an observation, not a rollback guarantee. A dropped/malformed answer after dispatch is uncertain. Reports contain fixed non-secret failure codes, never raw SDK exception payloads.

Limits: eight in-flight/candidate/active/retiring sessions per instance; sixteen concurrent calls per session; at most 20 metadata requests; 256 tools and 4 MiB catalog/HTTP bytes; 1 MiB business argument cap; total discovery budget at most 15 s, call budget at most 30 s. TTL hints clamp to 1–60 s, one per generation. Stdio uses the SDK's 4 MiB frame bound. Its stderr is drained with zero retained content, and >65,536 bytes ends the session. Node/schema validation and SDK implementation still run trusted in the owner process; this is not a hard owner-process heap isolation claim.

## Correction round 1

The five Important review findings were addressed in source commit `8bb0d3859c1975c70f0285dc000558086e5fc95b`, based on `8a006f64093e9bc91f83ab0001f033059a150751`. The production API and owner responsibility described above still apply. M1 and M2 remain deferred to F. The fresh correction evidence directory is `/home/ryltsevmg/Projects/Ocean-artifacts/c18.4.1-fix1-MRUqVo`. It contains the command logs, exact pins, counters, synthetic profiles, unit paths and PID/start observations.

1. **I1, suspension at dispatch.** When any retirement returns unknown, the instance synchronously aborts the lifetime of every session before returning the evidence. Both final writers already consult that lifetime. A held native launch also consults it through its existing signal. The SQLite-backed HTTP controls held an authorized business call or a metadata list at the public writer while another candidate lost its cleanup observation. With the old code the business call completed and the held list reached the server. The corrected code refused both final guards, with zero new wire methods or effects after release. A separate test held the response after a real server effect. Suspension then settled the received call as uncertain, with one SDK attempt, one received call and one effect.
2. **I2, literal credentials in JSON.** Discovery and invocation now inspect actual string values and object keys for the exact lease before returning plain JSON to the owner. A synthetic credential containing both a quote and a backslash escaped the original serialization check in a tool description, a schema key and a reply text. The first two now yield a sanitized catalog refusal. The last yields a sanitized uncertain outcome after one dispatch and one effect. Credential syntax supported by the HTTP resolver is preserved.
3. **I3, durable publication proof.** The qualification owner opens one SQLite transaction, requires current metadata permission, uses the existing `currentServiceCatalog` policy to check active state and all three revisions, and compares canonical content of the persisted snapshot with the candidate's proposed snapshot. Reusing an existing catalog ID for a different tool list previously activated the unpublished SDK candidate. The regression now rejects it, accepts the actually published snapshot, and rejects that snapshot once the credential revision advances.
4. **I4, native wire evidence.** The previous proof's native host-side `dispatches` files count successful owner authorizations. They cannot independently establish receipt. The correction uses the public SDK server transport's `onmessage` callback to append each inbound `tools/call` to `workspace/received` before the SDK passes it to the business handler. The handler appends effects separately. The qualification host asserts the SDK attempt, owner authorization, received-call and effect counts. On the old instrumented server, the new drop assertion failed because the receipt log was empty despite a recorded effect. The new pure refusal case records one received call and zero effects. Earlier proof files and measurements remain available under their original provenance.
5. **I5, whole-discovery deadline.** Native discovery can release the caller at cancellation or expiry while a preflight filesystem operation unwinds. Its session stays counted against the eight slots, and `close()` joins the underlying discovery. When an SDK launch has begun, discovery continues through retirement evidence. The existing inventory and pin checks now honor the signal between entries/chunks. The launcher passes it to file fingerprint reads. Preflight systemctl and initial group observation use the same signal, and the subsequent spawn guard still checks it. The preflight test holds eight actual workspace inventories at their filesystem read. Previously both deadline and cancellation left callers waiting, and after release eight systemctl commands were attempted. Now all eight callers receive refusal while held, a ninth fresh request is refused for capacity, close waits for release, and the drained work records zero later systemctl calls, zero SDK starts and `never_started`. A blocked OS filesystem call can keep one slot occupied until it returns. This correction makes the caller's deadline and the capacity bound independent of such a syscall.
