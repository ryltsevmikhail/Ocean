## Contracts for 18.4

- `new OwnerScopeService(store: ServiceAuthorityStorePort, ownerId: string, now: () => number)` is a capability for the already authenticated owner actor. Its `issue(intent)`, `revise({grantId,revision}, intent)` and `revoke({grantId,revision})` return an `OwnerScopeGrant` or throw on refusal. Intent is exactly `id, subject, permissions, limits, mode?`. Authorship/time/version come from the trusted runtime. Issue defaults to autonomous. Revision preserves the previous mode when omitted. Grant revision CAS, current membership and immutable authority baseline are checked in the immediate transaction. Revoked records cannot be revised or recreated under the spent id through this interface. No model has the service or its raw storage port.
- Service permissions may have a `baselineCatalogId`. Owner issuance resolves it to the current complete snapshot matching the connection tuple. A supplied stale baseline is refused. An exact selection binds only named tools. Current-set requires the presented names to match the full current set and materializes those names. A stale current-set presentation cannot silently expand on issue. Changed/missing selected tools suspend independently; owner reissue or restoration of the approved definition can restore their eligibility. Comparisons use canonical name/description/input schema/output schema/annotations/definition digest and exclude SDK provenance.
- Explicit all-including-future covers genuinely new names, subject to the same account/target/limits and scope checks. Names present at owner issuance must still match their approved definitions. A name first added after the baseline has no owner-approved definition in that snapshot. There is no durable per-name first-use approval for future arrivals. In-flight calls always pin their actual full selected definition. Inert service grants without an owner baseline are conservative until owner issuance/revision; the migration grants nothing.
- `new ServiceCallAdmissionService({store,transport,restored,now,deadlineMs?,classify?,credentialContinuous?})` exposes `call(request, signal?): Promise<ServiceCallResult>`. `now` supplies epoch milliseconds for grant/approval policy. The invocation deadline is elapsed wall-clock milliseconds, defaulting to the existing 30,000 ms service deadline. `request` consists of the exact subject (`workspaceId, roomId, botId, projectId, taskId`), `connectionId, catalogId, tool, arguments, grantReference, taskRunId, attemptId, invocationId`. Extra authors, grant records or classification evidence in requests are refused. The result is `{code, outcome: ServicePluginInvokeOutcome | null}`. An admission refusal returns null outcome and no transport invocation. Service confirm mode returns `confirmation_required` pending the explicit owner workflow in 18.5.
- `ServiceCallTransportPort.invoke(input): Promise<ServicePluginInvokeOutcome>` takes frozen connection data and tool definition, `catalogId, arguments, invocationId, signal, deadlineMs` and a one-use synchronous `authorizeDispatch(): boolean`. Use this at the **actual send after all async preparation**, in the same synchronous continuation as the send. Do no business I/O before it. Return the existing observed/not_started/uncertain shapes, without retries. The adapter owns isolation, credential resolution/changes, session readiness, SDK send-boundary integration, argument-schema/host validation and bounded model-visible output. These are not qualified by the scripted transport tests.
- `classify(connection, tool, args)` is optional synchronous trusted host evidence for the exact target and operation. The default is a global, possibly mutating operation. Narrow hosting requires the host to qualify actual account, enforcement and canonical target against the current persisted trust tuple. A declaration/evidence-reference string, MCP annotation or a model-provided resource hint is insufficient. An account or repository selector also needs current matching verified-account/evidenced enforcement bindings. Truly broad connection grants can operate in the global scope with honestly unverified identity. Trusted reconciliation observations do not settle original holds.
- The optional `credentialContinuous(connection, baselineCatalog)` supplies trusted same-account evidence for these precise credential revisions. Credential-revision mismatch suspends old eligibility unless this callback certifies continuity. Never implement it as reference-string equality, a saved verified label, or identical schema. Endpoint/stdio configuration changes must advance trust in addition to config. Changes of trust including account/enforcement use the existing trust-revision CAS. Advancing trust leaves prior grants untouched and ineligible. Same reference with changed credential bytes must be represented by a new credential binding at the host. The application cannot detect unannounced external identity changes.
- `beginServiceCatalogRefresh(tx, id): ServiceConnection` checks active persistent metadata permission and advances the config axis before discovery. `publishServiceCatalogRefresh(tx, completeSnapshot): boolean` publishes only an exact matching tuple in one transaction. A failed/interrupted refresh leaves the previous pointer as historical data with a stale tuple. Session availability is a transport fact and has no grant transition. An unrelated catalog publication can leave an in-flight call eligible only on its frozen tuple, tool and resource facts. Admission never redirects it to a new account, credential or changed definition.
- `SqliteStore.serviceAuthority.atomic(fn)` keeps its synchronous, immediate, same-DB semantics. Additional transaction methods are `participates(subject)`, `runMatches(request)`, `grantCalls(run, grantId)`, `claim(request, fingerprint, admission)`, `pending()` and `settle(request, terminalOutcome)`. They share the existing journal and are lifetime-guarded like the C18.2 methods. Admission reads the actual dispatching chat turn/target membership. A coding-task link must match a reserved dev task, its owning room/bot/workspace and the project identity. Review continuations and restored quarantine are closed. Runtime callers supply the host's restored status.

## Coding path and finalization

The existing request/decision/consume/claim/execute/record/settle pipeline is retained. A host-prepared guarded edit or registered test may select an applicable autonomous grant for the configured owner; overlapping confirm scope conservatively requests the existing owner decision. A matching grant reference is fixed on the pending exact approval and rechecked at decision, consume and worker send. A revoked/mismatched selected grant cannot fall back to the previous automatic approval. No owner decision is synthesized or persisted for automatic work. Unguarded legacy operations retain the existing owner path. Raw owner scope never adds apply, shell, commit, push or deploy backends.

The existing approvals and `ocean_coding_approval_claims` retain their original keys/fingerprints. The optional immutable approval fields are `grantReference` and `guardedDispatch: true`. The consumed decision, allowed-approval digest and journal state remain correlated. Approval admission requires current membership/dev capability, reserved task, exact registered test preview, both original/worktree leases, project/worktree/source/limits/toolchain binding, bounds and no conflicting effect. At final guard, SQLite joins the exact coding claim and still-started journal row by tool, run, attempt, invocation, approval key and SHA-256 of the allowed approval. Conflict inspection excludes only that own started identity, never a different attempt matching its invocation ID.

The tools-node operation carries its guard through actual edit/command backend preparation. The sandbox's ready-handshake observes the cgroup, rechecks toolchain/mount/source binding after async preparation and then calls the current-authority guard immediately before writing the worker payload. The bounded tests drive that same send helper with an in-process writer. A confirmed pre-send refusal settles not_started; a failure after sending remains uncertain. Finalization checks the recorded grant/binding and normal test evidence. A zero-send guarded claim can become quiescent only with its matching journal and absent test evidence. Older standalone and contradictory claims retain their conservative behavior. No installed worker process or native sandbox behavior was qualified here.
