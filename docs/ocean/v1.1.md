# Ocean 1.1: coding tasks and diff review

Status: proposed, not implemented. Ocean 1.0 remains the released text-only baseline.

## Outcome and user flow

The owner starts a coding task from a private dev room or Ocean Team. Dev can inspect project files, propose precise edits, and run approved test presets. Review evaluates the actual resulting diff and recorded test results. The owner decides whether to apply the reviewed result to the project.

1. Register the project and local test presets; inspect canonical root and current Git revision.
2. Start a task against a clean checkout. Ocean creates a dedicated worktree and branch `codex/ocean/<taskId>`; the original checkout is not the execution directory. A dirty checkout is refused with an explanation; no automatic stash, reset or cleanup of user files.
3. Ask dev to implement the task. Reads are limited to the task worktree. Each write displays the exact patch and requires allow-once or deny. Each test displays its full registered invocation and requires separate allow-once or deny.
4. Dev produces a result. The runtime captures a stable changeset and test evidence; dev's narrative is not evidence that files changed or tests passed.
5. The owner explicitly hands that changeset to review. Review sees bounded before/after file content, the complete diff and relevant test metadata/logs, not the private dev conversation. Review cannot write or execute.
6. A review verdict identifies the exact changeset hash. New edits or test-generated source changes make the previous review stale.
7. The owner approves application of the exact reviewed changeset. The host checks the original checkout is still clean at the same base; otherwise application is refused for reconciliation. Applying files does not commit, push, merge or deploy automatically.

Desktop, autonomous bot-to-bot loops, unrestricted shell, networked dependency installation, arbitrary Git commands and production deployment are outside 1.1.

## Existing implementation to reuse

- `packages/application/src/turn.ts`: provider/tool orchestration and durable task lifecycle.
- `packages/application/src/tools.ts`: immutable prepared operation, permission boundary, claim before effect, no replay of uncertain effects.
- `packages/tools-node/src/executor.ts`: file previews, size limits and stale-read checks.
- `apps/cli/src/tui/approval.ts` and `apps/cli/src/acp/permissions.ts`: presentation and cancellation patterns.
- SQLite task/event/claim storage, conversation receipts, M4 recovery and M5 snapshot/restore.

The current native backend explicitly advertises no filesystem/process containment and no confirmed tree stop. Its command runner conservatively returns uncertain even on leader exit. It cannot be enabled unchanged for normal chat test execution. `DirectChatService` currently always supplies `tools: undefined`; tool authority must be an explicit task-scoped application dependency, never a boolean supplied by a model.

## Authority and execution boundary

Use a local Linux sandbox worker with no provider credential. Bubblewrap and systemd-run are present on BigPC; their presence is not qualification. A prerequisite spike must demonstrate filesystem isolation, descendant accounting and reliable cleanup before command capability can be enabled.

- The host owns SQLite, model requests, approval UI, trusted Git operations and immutable changesets.
- The worker receives only a task-scoped request over private IPC. Mount only the task worktree writable, approved toolchain/dependency roots read-only, isolated proc, private temporary directory and empty HOME.
- Never bind the host root or full home. Hide Ocean profiles, backups, saved key, SSH credentials, user bus sockets, host proc and Git administration paths. Remove provider/environment secrets; disable network for test workers.
- Start the worker inside a supervised user systemd service/cgroup before executing project code. Do not expose writable cgroup control or the host user bus inside the sandbox.
- Stop the whole unit/cgroup, wait for verified emptiness and record evidence. Leader exit, pipe close and PID liveness alone cannot confirm cleanup. If unavailable or unverified, retain uncertain and block new effects.
- File read/write workers use the same filesystem boundary. Existing single-link and no-symlink checks remain; namespace isolation does not replace stale-content checks.
- A worktree is isolation of changes, not a security sandbox. Dependency and toolchain mounts must be enumerated and tested, including pnpm symlink targets; do not solve resolution failures by mounting the entire home.

Fallback is explicit read-only/text-only operation with a diagnostic reason, never automatic uncontained execution. No root access or global service configuration is part of normal operation.

## Policies and approvals

Capabilities are task-scoped: dev = bounded project read, proposed write, registered test presets; review = immutable changeset read. Role prose and bot handle do not grant authority. Existing bot profiles migrate to text-only; the owner binds capabilities explicitly for a project/task.

Only the owner can decide through trusted CLI/TUI approval ports. Model output and imported messages cannot approve an operation.

Each approval binds taskId, workspace/worktree identity, roomId, botId, run/attempt/invocation, operation type, exact patch or preset invocation, source tree hash, policy version and limits. A 5-minute expiry and any changed binding invalidate it. Persist the exact preview and owner decision before claiming/executing. Use allow-once only for writes/commands in 1.1; no allow-session, bulk yes flag or redirected-stdin approval. Denial/cancel before dispatch leaves files untouched and creates no started effect.

A test preset is an exact executable/argv/cwd and restricted environment, with qualified toolchain identity and limits. Initial presets for Ocean: test, typecheck, lint and build. The owner registers them; the model selects preset IDs, not a shell string or additional flags. Initial limits: 60 seconds, 32 KiB retained output, bounded process count and memory established by the spike. Exit 0 is a passed test only after confirmed cleanup and unchanged relevant source snapshot. Output truncation and nonzero exits are visible.

## Persistence and recovery

Introduce schema 6 with additive, transactional migrations from 5: coding tasks/worktree bindings, versioned task capabilities, approval requests/decisions, tool operation bindings, immutable changesets, test evidence, review verdicts and application receipts. Preserve all existing events/claims and support old fixtures. Do not reinterpret M4 room continuation acknowledgement as tool authorization.

Persist admission and operation identity before effects. After interruption do not replay writes, tests or application automatically. A write's unknown result requires content reconciliation against its exact before/after snapshot. Process cleanup evidence can settle process liveness, not prove that no file effects occurred. An unknown multi-file application remains held until per-file reconciliation.

Backup includes all new authoritative records. Worktree contents and immutable changeset content are external assets with manifests/hashes: snapshot copies must include referenced assets or declare themselves metadata-only and unusable for full coding-task restore. Restore remains text-only until the owner rebinds the project and external-effect interval is reconciled; no restored approval is executable.

One project mutation lease spans all rooms and entry points, including trusted host application and test execution. Existing global unresolved claims remain globally blocking. Read-only review of an already frozen artifact can proceed independently.

## Review contract

A changeset includes base commit, exact paths, before/after blobs, file modes, additions/deletions, bounded diff chunks and a content hash. Capture tracked changes and relevant untracked new files; do not treat Git's default tracked-only diff as complete. Exclude credentials, ignored dependencies, Git internals and unsupported binary/symlink changes. Refuse oversized/incomplete artifacts instead of silently asking for a verdict on a truncated diff.

Review input binds changeset hash, base, test evidence hashes and explicit context grants. Findings include path, line anchor, severity and explanation; verdict is approve / changes_requested / insufficient_context. A model verdict is advisory and never applies changes. Missing tests, stale tests, truncated logs or unreviewed files cannot be shown as fully verified.

## Acceptance and delivery

Acceptance example: on a temporary Ocean clone, dev changes a small function and regression test; the owner approves the exact writes and a pnpm test preset; the real tests pass in the qualified worker. Review receives the complete resulting diff, identifies a seeded defect, dev repairs it with another approval, tests rerun, a fresh changeset is reviewed, and the owner applies it to an unchanged original checkout. Direct and group rooms follow the same service.

Required negative cases: denied write/test; wrong room/bot/task approval; stale preview/expired decision; source changed during tests/review; malicious test reading the saved key, profiles or host proc; sandbox network access; escaped descendants; hidden new files; dirty source checkout; crash after claim/write/test/application; duplicate request; asset-missing restore; legacy CLI/ACP bypass. No external effect is retried or falsely marked stopped.

Deliver incrementally: capability/lease model → task worktree and snapshots → qualified worker → durable approvals → dev chat tools → review/application → recovery and RC. Coding features stay disabled until their prerequisite qualification gates pass. See the [implementation plan](../superpowers/plans/2026-11-02-ocean-1.1.md).
