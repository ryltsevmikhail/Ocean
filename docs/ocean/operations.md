# Эксплуатация и выпуск Ocean 1.0

Руководство для будущего локального выпуска Linux x86_64. Целевые команды `ocean init`, `doctor`, `backup` и `restore` ниже реализуются и проверяются на M5. Сегодня на БигПК рабочее дерево находится в `~/Projects/Ocean`; для разработки действуют [команды README](../../README.md).

## Как собрать и установить кандидата

1. Ответственный за выпуск выбирает зафиксированную ревизию с чистым деревом и версией пакета/CLI. Указывает точный Node, pnpm, хеш lockfile и минимальные системные требования. До появления такой ревизии выпуск блокируется.
2. В чистом каталоге выполнить `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm build`, `pnpm format:check`. Собрать архив `ocean-<version>-linux-x64.tar.gz`. Внутри — `bin/ocean`, собранные ESM-пакеты и их runtime-зависимости со всеми доступными точками входа, LICENSE, NOTICE, инструкция оператора и манифест. Launcher проверяет квалифицированную версию Node. История, профиль, тестовые базы и секреты в архив не попадают.
3. Вычислить SHA-256 финального архива и сохранить отдельно в записи кандидата, привязанной к ревизии. Оператор получает контрольную сумму по доверенному каналу. До распаковки сверить сумму; упаковочный тест отклоняет абсолютные пути, переходы через родителя и ссылки за пределы корня.
4. Распаковать архив в новый каталог `~/.local/lib/ocean/releases/<version>`. Установить пользовательский launcher `~/.local/bin/ocean` через ссылку `current` в дереве установок. Предыдущий каталог сохраняется. Повторная установка той же версии сверяет хеш. Незнакомый существующий файл не перезаписывается.
5. На тестовом профиле без исходников, сборочного кеша и pnpm проверить `ocean --version`, `ocean doctor`, `ocean demo --json`, затем создать профиль через `ocean init --workspace <dir>`. Проверка обязана выявлять неразрешённые workspace-ссылки.
6. Для живого smoke задать ключ DeepSeek в окружении процесса через принятый локальный способ управления секретами. Создать dev и review, пройти прямую и групповую переписку по Q12. Отдельно выполнить отказ на запрещённое действие. В карточку выпуска занести результаты без пользовательского содержимого.

## Как пользоваться

Создать профиль один раз в тестовом workspace. В примере `review` и `dev` — адреса созданных ботов; идентификаторы комнат печатает CLI. Выполнять в установленном Ocean 1.0.

```sh
ocean bot add --handle dev --name Разработчик --role "Предлагает изменения"
ocean bot add --handle review --name Ревьюер --role "Проверяет изменения"
ocean room direct --bot dev
ocean room group --name Команда --bot dev --bot review
```

В прямом диалоге отправить первый вопрос, закрыть TUI, открыть его вновь и задать уточнение. В группе отправить задание разработчику через `--to dev`, после ответа передать его ревьюеру через `--to review`. Скопировать roomId только из вывода соответствующей команды. Подробные правила ввода и обработки ошибок — в [контракте интерфейса](interface.md).

## Обычная работа и диагностика

`ocean doctor --json` сообщает версии CLI, Node и схемы, доступность профиля, права каталога, состояние владельца, наличие ключа как логический флаг, число незавершённых запусков, класс последней ошибки и время последней проверенной копии, если оно известно. Проверка по умолчанию локальная. Она не вызывает модель, не захватывает профиль у работающего процесса и не чинит базу. При активном владельце непроверяемые поля помечаются unavailable. В TUI статус доступен через процесс-владелец.

Сигналы оператору — ошибка записи, неподдерживаемая схема, заблокированные действия, ошибка провайдера и сбой последней резервной копии. Статусы и история доступны локально. При инциденте сохранить версию, время, код ошибки, идентификатор запуска и безопасную диагностическую сводку. Оповещение сторонних сервисов не требуется для работы 1.0.

| Ситуация                                                            | Действия оператора                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Профиль занят                                                       | Перейти к активному TUI или штатно завершить его. Проверить процесс. Не удалять запись владельца вручную.                                                                                                                                                        |
| Недостаточно места или ошибка SQLite                                | Прекратить новые записи, сохранить файлы, освободить место вне профиля, проверить целостность на копии. Возврат к записи только после успешной проверки.                                                                                                         |
| Ключ отсутствует, провайдер ограничивает запросы                    | Проверить конфигурацию в окружении, читать уже полученную историю. Новый оплачиваемый запрос требует явной отправки после проверки предыдущего.                                                                                                                  |
| Неизвестный результат или незакрытый инструмент                     | Открыть run review. Для разговора доступно подтверждённое оператором продолжение без инструментов. Завести блокирующий дефект. Перед возвратом провести затронутые Q и проверку восстановления. |

## Копия и проверка восстановления

Целевые операции — `ocean backup --to <новый-каталог>` и `ocean restore --from <копия> --profile <новый-профиль>`. Оператор делает копию перед обновлением и после каждого рабочего дня с новыми сообщениями. Для базового локального профиля целевой RPO — один рабочий день при соблюдении этого графика, целевой RTO — 30 минут на восстановление из проверенной копии. Это цели испытания, не измеренный результат. Держать минимум две проверенные версии, одну на другом доверенном носителе. Бессрочное хранение истории по умолчанию действует внутри профиля; целиком удалить профиль и копии может только его владелец отдельным осознанным действием.

1. Остановить владельца и исключить новый запуск общей блокировкой обслуживания. Сделать через SQLite backup API согласованный снимок, включая данные WAL. Отдельное копирование одного открытого sqlite-файла небезопасно.
2. Добавить конфигурацию без секретов, версию схемы, версии бинарника и snapshot format, время, число комнат/сообщений, последнюю позицию каждой комнаты, число незакрытых claims и SHA-256 каждого файла. Ограничить права. Проверить integrity_check, foreign_key_check и контрольные суммы копии.
3. Восстанавливать только в новый закрытый каталог. Сверить манифест и права, открыть подходящей версией в режиме просмотра, сверить позиции и незакрытые действия. Убедиться, что тестовое открытие не отправило запрос модели и не запустило инструмент.
4. Резервная копия могла предшествовать реальному внешнему действию. Восстановленный профиль начинает работу с отключённым внешним исполнением. Установить границу утраченного интервала из исходного журнала или независимых подтверждений. При невозможности сверки допускается только чтение или явно выбранный новый текстовый ход с предупреждением о возможной прежней оплате. Старые запросы не отправляются повторно.
5. Зафиксировать, кто проверил восстановление, длительность и фактические потери. Если RPO/RTO не пройдены на тестовом наборе Q10, исправить процедуру до релиза. Рабочие файлы проекта и секрет провайдера восстанавливаются отдельно от профиля Ocean.

## Обновление, откат и решение о выпуске

Для обновления остановить старую версию, сделать и проверить снимок, провести пробную миграцию на копии. Подготовить новый каталог версии. В окне обслуживания мигрировать рабочую базу один раз, проверить целостность, переключить `current` атомарной заменой ссылки. Сначала открыть профиль для чтения и выполнить doctor, затем разрешить новые записи и внешний вызов. Вести запись исходной и конечной версии и границы переключения.

При сбое до первой новой записи вернуть старый бинарник и совместимый проверенный снимок при подтверждённом отсутствии внешних эффектов после снимка. При сбое после новых записей остановить приём, сохранить оба состояния, оценить изменения и подтвердить допустимый объём потери. Сначала рассмотреть исправление вперёд. Старый бинарник с несовместимой новой схемой запускать нельзя. Восстановление всегда использует ограничения предыдущего раздела. Откат файлов программы не отменяет действия агента в workspace или у провайдера.

Карточка кандидата заполняется при RC в закрытом хранилище свидетельств. Обязательные поля — версия и ревизия, хеши lockfile и архива, Node и ОС, версия схемы до/после, время и исполнители проверок Q01–Q12, путь к обезличенным результатам, измеренные backup/restore и откат, известные дефекты, оператор релиза и решение владельца go/no-go. После первой установки добавить версию фактического артефакта, результат smoke и состояние профиля. Факт выпуска фиксируется только после успешного smoke. Ключи, дампы и реальные переписки в карточку не включать.
