# Данные и восстановление Ocean 1.0

Целевое расширение существующего SQLite-хранилища. Опорные реализации — [открытие базы](../../packages/store-sqlite/src/schema.ts), [журнал действий](../../packages/store-sqlite/src/tool-journal.ts), [владение процессом](../../packages/store-sqlite/src/ownership.ts). В базе сейчас версия 1. Таблицы комнат появляются с версией 2. События TaskRun сохраняют действующий формат.

## Логическая схема версии 2

| Отношение           | Основные поля                                                                                                       | Обязательные ограничения                                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| ocean_workspace     | id, canonical_root                                                                                                  | Один workspace в профиле, канонический путь уникален                                                                                 |
| ocean_bots          | id, workspace_id, handle, name, role, provider, model, profile_version                                              | PK id, UNIQUE(workspace_id,handle), version ≥ 1                                                                                      |
| ocean_rooms         | id, workspace_id, kind, title, direct_bot_id, next_seq                                                              | kind direct/group, UNIQUE(workspace_id,direct_bot_id) для direct, direct_bot_id пуст для group                                       |
| ocean_members       | room_id, bot_id                                                                                                     | PK(room_id,bot_id), оба из одного workspace; локальный владелец профиля — неявный человек-участник                                   |
| ocean_messages      | id, room_id, seq, author_kind, author_bot_id, target_bot_id, body, reply_to, turn_id, created_at                    | UNIQUE(room_id,seq); автор-бот и адресат состоят в комнате; reply_to принадлежит той же комнате; одно итоговое сообщение бота на ход |
| ocean_turns         | id, room_id, inbound_message_id, bot_id, read_through_seq, profile_snapshot, task_run_id, dispatch_phase, room_hold | UNIQUE(inbound_message_id), UNIQUE(task_run_id); частичный уникальный индекс на room_id при установленном room_hold                  |
| ocean_receipts      | request_id, operation, binding, object_ids                                                                          | PK(request_id); привязка включает операцию, workspace, отправителя, адресата, комнату и нормализованные аргументы                    |
| ocean_reviews       | id, task_run_id, effect_ref, actor, observed_version, disposition, reason, at                                       | Только добавление. Версия фиксирует, какое состояние видел оператор. Уникальный идентификатор решения                                |
| ocean_final_results | turn_id, expected_run_version, final_text, usage_ref, stop_reason                                                   | PK(turn_id). Сохраняются полный разрешённый к публикации ответ и связь с зафиксированным учётом использования                        |

ID непрозрачны. Межтабличные ссылки защищаются FK, включая составные ссылки там, где возможна подмена комнаты или workspace. Ограничения на состав группы и наличие профиля проверяются внутри одной пишущей транзакции. Последовательность выдаёт runtime в SQLite, время не участвует в сортировке. Memory-адаптер обязан давать те же квитанции, ошибки и порядок.

## Путь одного сообщения

1. В `BEGIN IMMEDIATE` проверить квитанцию. При новой команде разрешить адресата, проверить ограничения комнаты, присвоить seq и сохранить сообщение. Для назначенного хода создать запись turn с зарезервированным taskRunId, снимком профиля, границей истории и блокировкой комнаты. В той же транзакции записать квитанцию. Реплика без адресата заканчивается здесь.
2. После commit связать turn с TaskRun через идемпотентную CreateTaskRun с детерминированным ключом этого хода. Перед возможным обращением к модели сохранить номер попытки и фазу dispatch. Сбой в промежутке между записью dispatch и ответом оставляет возможный внешний эффект. Повтор send только читает квитанцию.
3. Сохранять расход токенов через существующий механизм. Для инструментов оставить цепочку prepare → approval → durable claim → execute → settle. Положительный ответ модели ещё не подтверждает побочный эффект инструмента.
4. После полного валидного ответа, учёта usage и проверки разрешённого текста записать ocean_final_results. Терминальное событие Complete разрешено только при наличии этой записи для чата. Отдельная локальная операция завершения идемпотентно фиксирует событие через прежний TaskRunService. После подтверждённого succeeded в одной транзакции вставить публичный ответ по уникальному turn_id, освободить room_hold и завершить фазу публикации. Отменённый/устаревший ожидаемый переход отклоняет публикацию.
5. При старте под эксклюзивным владельцем **сначала** завершить локальные незаконченные публикации с проверкой фазы и версии, **затем** применять общую reconciliation. Этим сохраняется подготовленный ответ при сбое до Complete. Состояние и версия, несовместимые с подготовленным результатом, переходят на ручной разбор. Сокращённая строка summary существующего TaskRun непригодна для восстановления текста.

### Освобождение комнаты и повтор

До dispatch с подтверждённым отказом в допуске, а также при известном терминальном отказе без незакрытых эффектов, runtime фиксирует итог хода и в той же транзакции снимает room_hold. Отказ в отдельном инструменте может вернуться модели в рамках той же попытки. Неполный или оборванный stream после dispatch требует отдельной классификации. Обычная ошибка сети не доказывает отсутствие обработки на стороне провайдера. Поздний ответ старой попытки после ручного разбора сохраняется только как свидетельство и не публикуется как новый ход.

Если storage не подтвердил commit, клиент запрашивает квитанцию по изначальному ключу через повтор того же send. Он никогда не заменяет ключ автоматически. При ошибке записи settlement движок прекращает внешние вызовы до восстановления. Перед каждым новым внешним действием права, состояние комнаты и незакрытые claims проверяются заново внутри критического участка. Текстовый режим передаёт пустой набор инструментов провайдеру и отказывает при попытке прямого обращения к исполнителю.

## Что делать после прерывания

| Сохранённый факт                                                          | Допустимое действие                                                                                                                                             |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сообщение принято, dispatch ещё не разрешался                             | Достроить локальные связи. Показать прерванный ход. Отдельное явное решение пользователя может начать новый ход после подтверждения отсутствия dispatch.        |
| Подготовлен финальный результат, либо успешный TaskRun ещё не опубликован | Завершить только локальные операции по пунктам 4–5. Не вызывать провайдера или инструмент.                                                                      |
| Модель могла получить запрос, но терминального результата нет             | Сохранить неопределённость и возможный расход. Предложить оператору просмотр, не повторять оплачиваемый вызов автоматически.                                    |
| Журнал содержит started/uncertain                                         | Восстановить uncertain по существующему контракту. Сохранить глобальную блокировку новых инструментальных claims, включая legacy-записи без привязки к комнате. |
| Запрошена отмена                                                          | Завершить cancelled только при доказанном прекращении работы. Иначе показывать cancelling с причиной.                                                           |

**Продолжение разговора.** `run review` показывает ID, фазу, известные последствия, статус журнала и почему работа стоит. Владелец может подтвердить `acknowledge --text-only` после предупреждения о незавершённом эффекте. Одна транзакция сверяет версию, записывает решение, снимает удержание очереди комнаты и переводит её в текстовый режим. Старая попытка сохраняет фактический исход. Следующая явная реплика создаёт новый TaskRun без инструментов и может повлечь отдельный платный запрос. В историю добавляется служебная отметка о прерывании. Конфликт версии требует повторного просмотра.

**Инструментальное исполнение.** Решение человека само по себе не очищает глобальный журнал. При доказанном исходе адаптер сверяет неизменяемую идентичность операции и положительное свидетельство выполнения либо отсутствия запуска. Переход по версии, свидетельство и решение фиксируются атомарно; для того же invocation повтор запрещён пожизненно. Без реализованного и проверенного источника положительного свидетельства соответствующее действие остаётся неопределённым. В частности, штатный Node backend не подтверждает остановку потомков. В целевом профиле комнат 1.0 shell изначально выключен. Допущенные файловые операции и одобрения проверяются отдельно. Восстановление БД из старой копии или открытие новой комнаты не служит доказательством безопасности повторного исполнения.

## Миграция и целостность

1. Остановить все процессы-владельцы на этом профиле. Проверить старую версию, свободное место и сделать проверяемую копию по [инструкции оператора](operations.md).
2. Сначала открыть базу для проверки без изменения схемы. Захватить эксклюзивное право мигратора до любых DDL; обычный запуск обязан соблюдать ту же блокировку. Текущий базовый путь вызывает openDatabase до acquireOwnership, поэтому для версии 2 нужен отдельный вход. Новая или неизвестная версия, живой владелец или повреждённая база останавливают миграцию.
3. В транзакции создать таблицы, ограничения и индексы, проверить старые счётчики, события, квитанции и незакрытые claims, выполнить foreign_key_check. Записать версию 2 последней и зафиксировать транзакцию. Не создавать комнаты из старых TaskRun без сохранённых сообщений.
4. Сравнить число и контрольные суммы старых записей до и после, открыть новым кодом, повторить открытие. На тестах оборвать миграцию посередине и проверить целую старую или новую версию. Откат после новых пользовательских записей требует отдельного решения о сохранении данных.
