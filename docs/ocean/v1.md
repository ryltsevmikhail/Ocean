# Ocean v1 — план поставки

Цель первой версии — один пользователь работает с несколькими именованными ботами в терминале. В личном чате отвечает выбранный бот. В группе разработчик и ревьюер видят общую переписку, а пользователь решает, кому передать работу. Разговор можно закрыть и продолжить после перезапуска.

Готовая база описана в [архитектуре Ocean](../ARCHITECTURE.md). Планируемые правила комнаты и запуска — в [модели Ocean](conversations.md), выбор заимствований — в [карте доноров](donors.md).

Эти этапы соответствуют M0–M4 [общего плана выпуска](production.md). После них обязательны M5 (установка и эксплуатация), квалификация RC и решение о выпуске.

## Этап 0. Исходная точка — выполнен

Самостоятельный локальный TS workspace с лицензией, lockfile и тестами. Из нового каталога доступны установка с зафиксированным lockfile, проверка типов, lint, тесты, сборка и демонстрационный запуск без обращения к провайдеру. Это позволяет сравнивать следующие изменения с работающим исходным состоянием.

## Этап 1. Профиль бота и история комнаты — выполнен

Добавлены типы профиля, личной комнаты и сообщения, а также прикладные команды и запросы с одинаковыми правилами для memory и SQLite. Состав личной комнаты хранится в таблице membership. Реализована миграция схемы 1→2 с сохранением TaskRun. См. [API M1](../integration/conversations.md). Состояние, которого старый runtime не сохранял, из старых задач не реконструируем. Начать с одного пользователя и одного workspace. Модель для этих проверок не нужна.

**Приёмка.** Создать двух ботов, открыть с каждым личный чат, записать сообщения, закрыть и открыть базу. Профили и порядок сообщений сохраняются. Повторное открытие личного чата возвращает прежнюю историю. В контекст первого бота не попадает переписка второго. При открытии базы предыдущей версии прежние события TaskRun читаются.

## Этап 2. Работающий личный чат — выполнен

Адресованный ход подключён к TaskRunService и runTurn через общий DirectChatService. Полный ответ сохраняется до завершения задачи. См. [реализованный M2](../integration/direct-chat.md). Добавить в CLI создание и выбор бота, отправку сообщения, просмотр истории и состояния хода. CLI и TUI используют один прикладной сервис. Для комнат обязателен постоянный режим хранения. Из журнала формируется контекст следующего хода. Отдельно сохраняются связь с запуском и итоговое сообщение. Код приложения управляет инструментами и запросом разрешения.

**Приёмка.** В терминале начать личный чат. На первом ходе назвать функцию, после перезапуска задать уточняющий вопрос. Тестовый провайдер получает исходное сообщение и ответ в верном порядке. Повтор отправки с тем же ID не вызывает модель повторно. Отклонённое пользователем редактирование файла оставляет файл прежним. Для первого ручного прогона достаточно текстового разговора.

## Этап 3. Групповая комната с явной передачей хода — выполнен

Добавлены создание группы из существующих ботов, список комнат и участников, адресация через --to и @упоминание, а также подписанная общая история в CLI/TUI. См. [реализованный M3](../integration/group-chat.md). Проверять членство по стабильному идентификатору. В TUI показывать автора и адресата, текущего исполнителя и состояние запуска. В v1 один ход в комнате активен одновременно.

**Приёмка.** Создать группу из разработчика и ревьюера. Пользователь вызывает разработчика, получает ответ, затем адресует проверку ревьюеру. Ревьюер видит ответ коллеги в группе. На каждое обращение создаётся ровно один TaskRun. Сообщение без адресата видно обоим, счётчик вызовов модели не меняется. Упоминание в ответе бота не запускает цикл взаимных ответов. Обе личные истории остаются отдельными.

## Этап 4. Перезапуск, отмена и приёмка функций — выполнен

Проверены границы хранения и исполнения, включая SIGKILL реального дочернего процесса на четырёх контрольных точках. Добавлены CLI/TUI разбора и атомарное подтверждение будущего текстового продолжения. См. [M4](../integration/recovery.md). Сделать видимыми для пользователя завершённый, активный и требующий разбирательства запуск. Сначала прогон со сценарным провайдером и временной SQLite-базой, живая квалификация DeepSeek выполняется отдельно на RC.

| Событие                                               | Ожидаемый результат                                                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Две отправки с одинаковым ID или потеря квитанции     | Одна запись сообщения и одно назначение. Несовпадающий повтор отклонён.                                                  |
| Сбой между завершением хода и отображением ответа     | Ответ восстанавливается ровно один раз из сохранённого результата. Повторного вызова модели нет.                         |
| Сбой после начала инструмента, до фиксации результата | После запуска видны задача и причина неопределённости. Инструмент не повторяется.                                        |
| Отмена во время model stream или команды              | CLI показывает запрос на отмену и подтверждённый либо неопределённый исход отдельно.                                     |
| Личные и групповые сообщения идут одному боту         | В запросе модели только разрешённая история нужной комнаты. Разрешение на действие в одном чате не переносится в другой. |
| Старый ACP-клиент открывает сессию                    | Инициализация, prompt, обновления и отмена продолжают работать по существующему контракту.                               |

**Граница выпуска.** В v1 входят профили, история, прямые и групповые чаты, явное назначение и диагностика выполнения. Нативное приложение, реальный многопользовательский доступ, автоматический диалог бот–бот и координация через GitHub — отдельные последующие решения. Без подтверждённой остановки дерева процессов команда остаётся с неопределённым исходом. Успешный тест переписки не квалифицирует изоляцию команд.

## Этап 5. Установка и эксплуатация — выполнен

M5 добавляет автономный архив Linux x64, установщик с проверкой SHA-256, сохранением версий и переключением current, doctor без захвата владельца, согласованный SQLite backup и проверяемое восстановление в новый профиль. Восстановленный профиль не допускает внешнюю работу без отдельного подтверждения нового текстового хода. См. [руководство оператора](operations.md).

Проверяются повреждённые и несовместимые данные, права и ссылки, WAL, сохранность неизвестных эффектов, история после restore, установка/обновление/откат без исходников. Следующий этап — RC: установленный артефакт, живая модель, ручной TTY и полная матрица приёмки. Выпуск 1.0 остаётся отдельным решением.
