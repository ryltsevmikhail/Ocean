# Ocean: автономные боты и прямой MCP

Дата: 2026-11-04. Статус: **направление принято; реализация не выполнена**.
Приоритеты, собственный локальный движок и подключение моделей через API
уточнены в [архитектуре платформы](../../ocean/platform-architecture.md).
При расхождении действует этот новый документ и
[план A–H](../plans/2026-11-04-ocean-platform.md).
Codex/Claude CLI-исполнители исключены: модели подключаются через ProviderPort,
а агентный цикл выполняет Ocean. Прямой MCP — слой инструментов, не движок.

Пользователь выбрал направление: сохранить runtime Ocean, перейти к прямому MCP,
выдавать постоянные полномочия на доверенную область и разрешить свободное
взаимодействие ботов. Детали ниже, помеченные как проектные решения, предложены
автором дизайна и ещё не являются реализованными возможностями продукта.

Исследован Ocean stable `388b974ece6142987b55fcb9da8cb8d8b1cea985`,
Executor SDK/MCP/OpenAPI `1.6.11`, текущие публичные исходники MCP TypeScript SDK
и DeepSeek Superagent. Незавершённые изменения остановленного исправления
Executor не входят в этот дизайн и не квалифицированы. Выпуск и реализация
остаются на паузе: текущий запрос пользователя разрешает только документацию.

## 1. Зачем меняем архитектуру

Ocean — локальная среда для постоянной команды ботов. Пользователь задаёт цель,
доступные ресурсы и пределы полномочий. Боты самостоятельно работают, обсуждают
результаты и делегируют задачи. Пользователь видит происходящее, может вмешаться,
остановить работу или отозвать доступ. Закрытие Desktop/TUI не останавливает команду.

Критерий успеха — законченная полезная работа с небольшими затратами внимания
человека. Количество подтверждений и количество реплик ботов не являются целью.

Согласовано пользователем:

- Автономность внутри доверенной области, без approval каждой команды и операции.
- Режим bypass permissions внутри этой области обязателен.
- Боты свободно общаются и делегируют; старое ограничение «один ответ каждого,
  без переговоров» больше не описывает целевой продукт.
- Разрешения сохраняются после перезапуска.
- Готовые MCP-серверы подключаются преимущественно настройкой, без разработки
  собственного плагина Ocean для каждого сервиса.
- Runtime сохраняет владение полномочиями, состоянием и восстановлением.

## 2. Варианты и выбранный путь

| Вариант                         | Что даёт                                                                     | Цена и решение                                                                                                                                                    |
| ------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Встроенный Executor             | Единые MCP/OpenAPI/GraphQL, каталог, подключения, credentials и policies     | Его состояние и политики пересекаются с Ocean; уже есть SDK patch и перехват внутренних действий. Не выбран основным backend                                      |
| Прямой официальный MCP SDK      | Подключение готовых HTTP/stdio серверов без дополнительной модели интеграций | Ocean поддерживает собственный небольшой host; OAuth, повторы, процессы и совместимость требуют проверки. **Выбран**                                              |
| Внешний Executor как MCP-сервер | Его интеграции без встраивания SDK в Ocean                                   | Дополнительный сервис и непрозрачное внутреннее исполнение; возможен позднее для реальной потребности в OpenAPI/GraphQL, не обязателен и не часть первой поставки |

Прямой MCP не означает реализацию JSON-RPC, OAuth или MCP с нуля. Используется
публичный API выбранного закреплённого SDK. Смена библиотеки не считается
обоснованной, если потребует частных API, vendor patch или сопоставимой обвязки
для подавления её внутреннего поведения. Это проверяется до миграции продукта.

## 3. Что берём из DeepSeek Superagent

Берём разрешение на поручение целиком (Mandate), отделение поручения от попытки
исполнения, сохраняемую доставку входящих сообщений, продолжение работы после
перезапуска и интерфейс, который привлекает внимание только по делу.

В прототипе `Sessions.ensure()` устанавливает `danger-full-access`; работники
используют Harness и собственные рабочие каталоги. Его `Executor` — порт
исполнения поручений, не `@executor-js/sdk`. Это не готовый backend Ocean.
Не переносим Cordis/Harness целиком, единственный репозиторий как ограничение,
запуск произвольных команд с правами пользователя без изоляции или предположение,
что текстовая инструкция обеспечивает техническую границу доступа.

Прототип не реализует в точности нашу свободную команду постоянных ботов:
он ограничивает доступ работников к другим сессиям. Общение Ocean проектируется
явно, а не объявляется полученным вместе с донором.

## 4. Существующая основа и границы изменений

Сохраняются domain/application/adapters, TypeScript, SQLite, один владелец профиля,
TaskRun/attempt, requestId/receipt, комнаты/история, подготовка вложений,
worktree/changeset, sandbox, журнал эффектов и протокол наблюдения клиентов.
Существующий локальный цикл Runne сохраняется; второго управляющего агентного
цикла, базы квитанций или владельца полномочий не возникает.

Текущие ограничения находятся не только в Executor:

- `plugin-catalog.ts` и grants зашиты под два GitHub read tools и repository.
- `plugin-session-authority.ts` связывает пригодность сессии с отзывом доступа.
- `plugin-catalog-tools.ts` требует полного совпадения каталога с manifest.
- `coding-dispatch.ts` проводит coding-операции через точное approval.
- `room-broadcast.ts` создаёт конечный набор ответов на пользовательское сообщение.
- `tool-journal.ts` блокирует новые claims при любом незавершённом эффекте профиля.

GitHub-пилот уже исполняет разрешённые чтения без пооперационного подтверждения.
Его ограничения не следует описывать как свойство всех MCP-интеграций.

Проектное решение: первая команда — существующая групповая комната и её состав.
Отдельная сущность Team не нужна до появления сценария, который нельзя выразить
этой моделью. Личные комнаты остаются полноценным вариантом работы одного бота.

## 5. Постоянные полномочия и bypass permissions

Runtime хранит постоянное разрешение владельца: кому оно выдано, какие проекты,
подключения и действия разрешены, ограничения ресурсов и версия политики.
Приём поручения фиксирует ссылку на это разрешение и область самой задачи.
Это расширение существующей модели задач/прав, а не второй журнал approvals.

Эффективные права — пересечение разрешения владельца, области поручения и прав
исполнителя. Внутри них bypass permissions означает автоматическое разрешение
операции без окна подтверждения. Проверка актуальности прав и запись эффекта
остаются автоматическими. Модель не создаёт owner grant и не подтверждает себя.

Проектное решение: режим выбирается для доверенной области. Поддерживаются
автономный режим и режим с подтверждениями; для новой явно настроенной доверенной
области основной сценарий — автономный. Импорт старого профиля не расширяет права.
Отсутствие разрешения не эквивалентно полному доступу.

Команды, редактирование, тесты и разрешённые сервисные записи исполняются без
дополнительных вопросов. Commit/push/deploy не запрещены навсегда на уровне
архитектуры, но доступны ботам только при явно включённых полномочиях этой области.
Разрешение оператору Codex выпускать Ocean не переносится автоматически на ботов.

Вопрос человеку возникает при необходимости расширить права или при выбранном
им правиле подтверждения, а не потому, что операция относится к записи вообще.
Запрос объединяется по требуемому расширению, чтобы не повторяться на каждом шаге.
Если расширение отклонено, бот ищет разрешённый путь или сообщает ограничение.

Технически ограниченная область обеспечивается sandbox, выделенными credentials
и ограничениями сервера. Одно перечисление путей в prompt не ограничивает bash.
Bypass не выключает изоляцию и не монтирует профиль, owner socket или секреты
в worker. Первая поставка не добавляет режим неограниченного доступа ко всей ОС.

Отзыв прав сохраняется атомарно и запрещает новые dispatch после его фиксации.
Уже отправленное действие остаётся в журнале; отзыв не доказывает его отмену.
При остановке используются существующие доказательства завершения процессов.

## 6. Общение, делегирование и продолжение работы

Боты получают host-инструменты для адресованного сообщения, поручения другому
боту и чтения состояния связанной задачи. Они не требуют подтверждения внутри
команды и доверенной области. Runtime устанавливает автора по контексту запуска;
поля автора и полномочий из модельного текста не принимаются как доказательство.

Сообщение хранит id, комнату, отправителя, адресатов, связь с задачей и причиной
отправки. При необходимости оно будит получателя или попадает в его текущую
очередь. Доставка и квитанция сохраняются до пробуждения; повтор доставки не
создаёт вторую задачу или вторую запись истории. Технические квитанции не будят ботов.

Обычная реплика может обсуждаться, но не обязана вызывать ответ всех участников.
Проектное решение: адресованные сообщения и назначенные поручения будят нужных
ботов; общая история доступна участникам как контекст. Общее пользовательское
поручение может инициировать работу нескольких ботов. Политика общения допускает
их дальнейшее обсуждение, без жёсткого правила «по одному ответу».

Делегированная задача ссылается на исходное поручение и его бюджет. Она не шире
родительских полномочий и полномочий получателя. Для использования более широкого
собственного доступа получателя нужна самостоятельная разрешённая задача, а не
маскировка расширения прав под пересылку сообщения. Доступ к чужим комнатам и
передача их вложений не возникают из одного факта знакомства ботов.

Существующие CodingTask и TaskRun остаются источниками состояния. Для обычных
поручений план должен определить минимальное постоянное представление задачи,
которое связывает несколько TaskRun и дочерние поручения, переиспользуя имеющуюся
модель там, где её смысл совпадает. Нельзя приравнивать поручение к одному ответу
модели, но нельзя и заводить второй аналог CodingTask без необходимости.

Проектное решение: SQLite inbox/outbox и существующий runtime scheduler;
без брокера сообщений, сетевого A2A и обязательного отдельного LLM-router.
Бюджет, параллелизм и учёт повторяющихся передач общие для корневого поручения.
Повторяющаяся цепочка без нового результата приостанавливается автоматически;
пользователь получает одно понятное сообщение. Конкретные пороги выбирает builder
и проверяет на принятом сценарии. Срок/лимит одной команды не равен сроку всей задачи.

Ожидание ответа коллеги не держит открытый SQLite transaction и не занимает
единственный слот комнаты. История получает последовательные номера при записи;
модельные вызовы независимых задач могут идти параллельно. Записи в один worktree
и применение одного changeset сохраняют координацию по ресурсу. Review по точному
changeset остаётся проверяемым; роль review в текущем coding-процессе сохраняет
чтение неизменяемого артефакта без команд и записи, но может общаться с коллегами.

## 7. Прямой MCP и готовые серверы

Продуктовое подключение содержит стабильный connectionId, транспорт HTTP/stdio,
endpoint либо закреплённую программу и аргументы, ссылку на secret store,
проверяемую идентичность аккаунта, политику доступных инструментов и состояние.
У HTTP-подключения фиксируется доверенный адрес; перенаправление не должно
незаметно переносить credentials на другой origin. Stdio запускается с ограниченным
окружением и управляемым деревом процессов. Каталог не исполняет команды установки.

Проектное решение: первый generic import принимает конфигурацию уже доступного
сервера, без собственного marketplace и автоматической установки произвольных
npm/git пакетов. Карточки проверенных серверов — удобные presets конфигурации.
Универсальный installer и OAuth каждого поставщика не являются условиями первой
поставки. Нужны ссылки на credentials и один проверенный путь авторизации;
заявлять OAuth поддержанным можно только после отдельной реализации и приёмки.

ServicePluginTransportPort сохраняется как заменяемая граница, но из неё и domain
убираются идентификаторы конкретного SDK и GitHub-only ограничения. Нейтральный
контракт содержит обнаружение возможностей, вызов, отмену/наблюдение где сервер
это поддерживает, и классификацию результата. Новые методы добавляются только
для доказанного сценария; весь MCP API заранее не зеркалируется.

Три состояния разделяются: долговечные права, текущий снимок инструментов,
временная транспортная сессия. Рестарт сессии не отзывает owner grant. Повторное
подключение и обновление метаданных разрешены ранее выданным доверием к connection.
Повторное подключение само по себе не повторяет прерванный бизнес-вызов.

Каталог публикуется атомарно; снимок выполняемого вызова не меняется в полёте.
Появление постороннего инструмента не ломает разрешённые инструменты. По умолчанию
новые инструменты не получают права автоматически. Владелец может явно доверить
весь набор инструментов подключения, включая будущие: это более широкое постоянное
разрешение, а не молчаливое расширение. Существенное изменение уже разрешённого
инструмента требует проверки соответствия политике; одной JSON schema недостаточно
для доказательства неизменной семантики. При несовместимости приостанавливается
затронутый инструмент, а не весь профиль.

Смена аккаунта, endpoint или расширение OAuth scopes отличаются от обычного
обновления access token. Политика привязана к аккаунту и разрешённым ресурсам,
не к строке токена и не к lifetime объекта SDK. Если идентичность нельзя проверить,
подключение честно указывает это; оно не выдаёт непроверенную непрерывность за факт.

MCP не задаёт универсального ограничения «только repository X». Оно обеспечивается
credentials, сервером либо явно описанным сервисным правилом. Без обеспечивающей
границы Ocean не обещает такую изоляцию. Часть интеграций может потребовать небольшого
адаптера; это не повод писать новый SDK/плагин для каждого сервиса.

Готовые MCP-серверы дают инструменты, но не гарантируют событийный вход.
Webhook/polling Sources и расписания — отдельный следующий этап. Свободное общение
ботов внутри Ocean не зависит от реализации внешних Sources.

## 8. Журнал, повторы и независимая работа

Сохраняются наблюдаемые исходы: не отправлено, ответ получен, результат неизвестен.
Полученный error не всегда доказывает отсутствие частичного изменения. Отмена
запроса не означает отмену операции на сервере. Гарантия exactly-once для внешнего
сервиса не заявляется без его идемпотентности или проверяемого результата.

Разрешены автоматические ограниченные повторы доказанно безопасных чтений,
метаданных и идемпотентных операций с сохранённым ключом. Повтор небезопасной записи
после неопределённого исхода не выполняется вслепую. Сначала бот или адаптер пытается
проверить исход разрешённым чтением. Самостоятельная сверка фактов не требует owner
approval; превращать предположение модели в подтверждённый результат запрещено.

Блокировка неопределённого эффекта относится к затронутому ресурсу/операции.
Она не останавливает несвязанных ботов и безопасное чтение для восстановления.
Неизвестные legacy claims без области остаются консервативными до сверки; миграция
не помечает их выполненными и не снимает блокировку без доказательства.

SDK retries, OAuth recovery и protocol renegotiation учитываются как реальные
сетевые попытки. Публичные настройки и квалификация должны обеспечивать выбранную
семантику; смена Executor на MCP SDK не считается таким доказательством сама по себе.

## 9. Миграция и поставка

Проектное решение: последовательная замена адаптера, не постоянные два backend.
Во время перехода сохраняется старый код для сравнения и отката разработки, но
одна операция выбирает один backend; fallback после неясного результата запрещён.
Новые feature capabilities позволяют клиентам отличать поддержку автономности.
Старый клиент не должен молча включать новые права или управлять ими неполным UI.
ACP сохраняет прежний контракт до отдельного совместимого расширения.

Миграция переносит существующие подключения, узкие grants и историю, не расширяя
их до команды или будущих tools. Незавершённые approvals и claims сохраняют смысл
и не превращаются автоматически в разрешённые операции. Новый автономный режим
включается явной настройкой доверенной области владельцем.

Реальный профиль, установленный RC2, RC1 и чужие worktrees не используются как
fixtures. Проверка миграции и rollback идёт на копиях/одноразовых профилях. Старый
бинарник не открывает новую неподдерживаемую схему; откат использует совместимый
backup. Незавершённое исправление Executor сохраняется отдельно до решения о его
нужности; оно не объявляется принятым и не теряется при смене backend.

Прежние ограничения «боты не общаются» и обязательное approval каждого действия
уступают этому дизайну после его принятия. Проверки точности changeset, прав,
изоляции и восстановления не отменяются. Старый release ledger сохраняется как
история; новый план должен явно связать заменённые и оставшиеся gates. Стабильный
выпуск не объявляется готовым по старому набору тестов после изменения семантики.

## 10. Приёмка нового пути

| Сценарий                         | Требуемый наблюдаемый результат                                                                                                  |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Работа внутри доверенной области | Бот редактирует, выполняет разрешённые команды и сервисные действия без пооперационных окон; в журнале есть основания доступа    |
| Работа команды                   | Бот A поручает работу B, B возвращает результат, A продолжает; всё без участия человека, с общей историей задачи                 |
| Перезапуск                       | Права и ожидающие сообщения сохранены; известные безопасные продолжения идут автоматически, неопределённые записи не повторяются |
| Выход клиента                    | Desktop/TUI закрывается; runtime и команда продолжают, второй клиент видит тот же результат                                      |
| Повтор сообщения                 | Потеря квитанции и повтор того же id не создают второй запуск; изменённый payload отклоняется                                    |
| Права и отзыв                    | Выход за область не исполняется; после отзыва новые dispatch запрещены; делегирование не увеличивает права                       |
| Каталог                          | Рестарт/TTL/новый посторонний tool не требуют полного regrant; более широкие права не возникают без политики владельца           |
| Прямой MCP                       | Настройкой подключаются GitHub HTTP и локальный stdio; дополнительный тестовый сервер не требует изменений domain                |
| Неопределённая запись            | Сервер принял запись и оборвал ответ: нет слепого повтора, виден unknown; независимая задача и разрешённая сверка продолжаются   |
| Параллелизм                      | Независимые ресурсы исполняются параллельно; один worktree защищён от конфликтующих изменений                                    |
| Цикл общения                     | Повторяющиеся передачи ограничиваются общим бюджетом/правилом прогресса; одно уведомление вместо потока вопросов                 |
| Остановка                        | Новая работа не стартует; состояние дочерних процессов и удалённых вызовов отражено честно                                       |
| Миграция                         | Старые узкие grants не расширились, история/вложения/receipts сохранены, rollback проверен отдельно                              |

До продуктовой миграции нужен небольшой сравнительный прототип на публичном API:
HTTP GitHub, stdio и синтетическая запись с потерей ответа, restart, catalog refresh,
401/404/protocol mismatch и отмена. Неудача этого gate возвращает выбор SDK на
обсуждение, а не запускает очередной vendor patch. Секреты и реальные данные в Git
не попадают. Внешние эффекты проверяются только на согласованных тестовых ресурсах.

После реализации обязательны root `pnpm check`, `pnpm build`, `pnpm format:check`,
строгая проверка test TypeScript без исключения известных ошибок, source <=300
физических строк и отдельная Linux/native/GUI/live приёмка замороженной ревизии.
Исторические результаты RC2 не заменяют эти проверки.

## 11. Что оставлено builder и что отложено

Builder выбирает конкретный релиз SDK, внутренние имена типов, минимальную схему
миграции, размещение модулей, пороги очередей/бюджетов и формат compact projections.
Он не меняет модель прав, не добавляет host full-access и не расширяет поставку
до нового общего agent framework. Архитектурные исключения выносятся на обсуждение.

Отложены расписания/ScheduleOccurrence, внешние Sources, marketplace/installers,
универсальный OAuth-каталог, сетевой A2A, обязательный Executor gateway и перенос
на Harness. Внешний design-worktree не меняется; минимальные клиентские изменения
для настройки и наблюдения нового поведения планируются через общий контракт.

MIT готовых серверов проверяется по конкретной версии. У текущего официального
TypeScript MCP SDK переход MIT/Apache-2.0; нельзя называть весь стек исключительно
MIT. Проектное решение — допустимы совместимые permissive зависимости с сохранением
LICENSE/NOTICE, а не неподдерживаемый SDK только ради старой надписи MIT.
