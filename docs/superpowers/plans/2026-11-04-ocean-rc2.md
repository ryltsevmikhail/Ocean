# Ocean RC2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an installed Linux RC2 with provider settings, one-answer-per-member broadcasts, real image understanding and the first scoped GitHub read-issues plugin.

**Architecture:** Extend the shared profile runtime and application services; Desktop/CLI/TUI remain clients. Credentials and image assets stay runtime-owned, with provider-neutral messages and adapter-only vendor/Executor dependencies. Durable identities precede fanout and network effects.

**Tech Stack:** Strict TypeScript, pinned pnpm, SQLite, current Linux sandbox, Electron/Vue, DeepSeek Chat Completions vision, qualified pinned Executor MCP/OpenAPI adapter.

**Spec:** `docs/superpowers/specs/2026-11-04-ocean-rc2-design.md` (approved product scope and confirmed broadcast semantics).

## Global Constraints

- Linux x86_64 Omarchy; TypeScript workspace; pinned pnpm; source files at most 300 physical lines; domain pure, application dependent only on domain, I/O behind public adapter ports.
- Runtime owns state/authority; model cannot approve itself; review reads immutable artifacts and has no command/write tools.
- Persist before effects; unknown effects are never automatically replayed; parent exit is not child cleanup proof; failed isolation leaves execution disabled.
- No automatic stash/reset/clean of source or user files; bots cannot commit/push/deploy; no keys, real profiles or sensitive transcripts in Git.
- Keep root checks, native behavior, actual GUI, live DeepSeek, live GitHub and credential-store verification separately attributed. Skips are not passes.
- Preserve installed Ocean 1.0 and the user's active Ocean RC profile. Preserve the separate audit branch/worktree and the eight owner-modified positions listed in the handoff.

## Review Focus

1. A disconnected or rotated provider cannot silently fall back to an old key after restart — Task 1 tests external credentials, rotation and restart.
2. A repeated/partially interrupted broadcast cannot duplicate a user message, a charge or a bot answer — Task 2 tests receipts, frozen context and partial failure/restart.
3. A missing/cross-room image or aggregate oversized request cannot become metadata-only inference — Task 3 tests authority, mixed-model broadcast and exact serialized size.
4. An Executor 401 or dropped response cannot repeat a business request, even after token refresh — Tasks 4–6 count actual requests and preserve journal uncertainty.
5. A release cannot lose user data through incompatible schema rollback or an obscured composer — Tasks 7–8 verify layout, migration/rollback and installed behavior.

**Interfaces:** `RoomBroadcastService.submit` accepts workspace/room/request ID/text/validated attachment references and returns a durable batch receipt with frozen recipient identities and child run IDs. `get`/observation expose each recipient's queued/running/result/refused/uncertain state. Note submission retains its no-model semantics. A context boundary supplies the same pre-answer room history to all children. Versioned owner recovery offers continue-known-not-started or abandon-known-not-started; continue is refused while any child is uncertain or a relevant hold remains.

- [ ] RED: two members produce one user record, two child runs, two provider calls and one answer each; identical retry returns original identities and changed data conflicts.

- [ ] RED: add/remove member mid-batch, wrong room/bot, mixed permissions, disconnect, cancellation before/after dispatch, lost receipt and SIGKILL after one recipient starts.
- [ ] Implement durable queue/admission/context anchoring and serialized room dispatch. Recovery pauses proven-undispatched siblings; explicit versioned continuation skips all completed children and requires known terminal outcomes for every started child. Uncertainty refuses continuation; owner abandonment cancels only proven-undispatched work and preserves unknown children/holds.
- [ ] Test pending-batch room admission (new model turns refused, notes/history allowed), stale owner recovery votes and existing text-only acknowledgement that cannot settle unknown effects or retry the batch. Expose the same recovery decisions in Desktop/TUI. Broadcast grants no coding rights.
